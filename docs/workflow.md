# 雑誌・書籍PDFへのマーカー付け

雑誌や書籍のPDFの記事（書籍は章）のうち、読みたいものだけを小さいPDFに切り出し、重要な箇所に3色でマーカーを付ける。
章・記事ごとの参考文献・関連リンクは、確認できたものだけを GitHub Issue のコメントにまとめる（下の「参考文献を集める」）。

- 元PDFは書き換えない。出力はいつも元PDFのコピーに注釈を追記したもので、再実行しても重複しない
- PDF はコミットしない（`.gitignore` で `*.pdf` を除外）
- 作業は `output/<PDF名>/`（元PDFの名前から拡張子を除いたフォルダ）で行う。雑誌も書籍も同じ規則。例: `Sample-Magazine-2026年10月号.pdf` → `output/Sample-Magazine-2026年10月号/`、書籍は `output/Clean-Architecture/`（下の「書籍を取り込む手順」）

## 新しい号を取り込む手順

以降のコマンドは `app/` で実行する（`cd app`）。号は `Sample-Magazine-2026年11月号` の例。

| 手順 | やること | コマンド |
|---|---|---|
| 0 | 号のPDF（元PDF）を `output/<PDF名>/` に置く | `output/Sample-Magazine-2026年11月号/Sample-Magazine-2026年11月号.pdf` |
| 1 | **記事を一覧にして、タイトルを見て対象にするか判断する** | `uv run python plan_issue.py --pdf ../output/Sample-Magazine-2026年11月号/<号>.pdf` |
| 2 | 対象・対象外を記録する | `... --include p100-105 p120-126` / `... --exclude p150-155` |
| 3 | 対象の本文を読み、**読み方を選択式で聞く**（目的・重点にする章・使う色）。答えを `reading.json` に残す | 下の「読み方を確認する」 |
| 4 | 本文を読み、3の答えに沿って重要箇所を `highlights/<ID>.json` に選ぶ（Claude と読みながら行う） | 下の「重要箇所の選び方」 |
| 5 | 一括で仕上げる（切り出し・ハイライト） | `uv run python build_issue.py --plan ../output/Sample-Magazine-2026年11月号/articles.json` |
| 6 | 章・記事ごとの参考文献を集め、リンクを確認して Issue にコメントする | 下の「参考文献を集める」 |

手順1の一覧は `articles.json` に残る。判断（`target`: `true` 対象 / `false` 対象外 / `null` 未判断）は、再実行しても消えない。

- **文字が取れない記事**（表紙・広告・文字化け）は、最初から対象外になる。`--include` で戻せる
- 記事の範囲は、PDFの目次（しおり。ビューアの左側に出るブックマーク）から割り出す（特集は章を含めて1記事、連載は1回で1記事）
- 記事のIDはページ範囲（`p100-105`）。`name` はファイル名・フォルダ名の日本語部分で、連載名から自動で付く（`articles.json` で直せる）
- 手順5は、重要箇所のJSONがある記事だけハイライトを付ける。無い記事は「重要箇所が未選定」と表示して、何も作らない（切り出しだけのPDFは作らない）
- 重要箇所のページ番号は、記事の範囲を切り出したPDFのページ（1始まり）で書く。確認用に切り出したいときは `uv run python split_pdf.py --plan ../output/Sample-Magazine-2026年11月号/articles.json`（`--only <ID>` で記事を絞れる。出力は `分割/<name>.pdf`）

## 書籍を取り込む手順

書籍は章単位に分ける。分け方の基準は次のとおり。

- **本編の章（第N章・特集・Rule など）だけを分割の対象にする**。前書き・はじめに・おわりに・あとがき・索引・Appendix・付録・参考文献・奥付・目次・カバー・表紙、部の扉（文字がほとんど無いページ）は、本編ではないので、対象外を提案する（`target` を決めるのは人）
- **30ページ未満の単位は、隣の章を足して、30ページ以上にする**（PDF を何度も開閉しなくて済むように）。30ページ以上になるまで、次の章を足す。足す相手は本編の章だけ（索引や付録は足さない）。間に部の扉があれば、一緒に含める。最後の単位が30ページ未満のまま残ったときは、直前の単位にまとめる
- 合体の結果が50ページを超えたときは、警告が出る（承認で確認する）。章の数の上限は設けない
- 合体した記事の名前は、最初と最後の章の見出しをつなぐ（例: `Rule1〜Rule3`）。長い題を `+` でつなぐと、ファイル名が長くなりすぎるため
- 自動の合体は `plan_issue.py --unit book --rebuild --auto-merge`。手で合体するときは `--merge`（下）
雑誌と同じ形（`articles.json` の「記事」）で持つので、色・ラベルはそのまま使える。

| 手順 | 誰が | やること |
|---|---|---|
| 0 | 人 | 書籍のPDFを `inbox/` に置く（フォルダは作らない） |
| 1 | Claude | `output/` の下に PDF 名（拡張子なし）のフォルダを作り、PDF をその中へ移す。例: `inbox/Clean-Architecture.pdf` → `output/Clean-Architecture/Clean-Architecture.pdf` |
| 2 | Claude | 分割案を作る（下のコマンド）。しおりがない・章の区切りが取れないときは、人が章名とページ範囲を伝える |
| 3 | Claude | 案を一覧にして人に見せる。ID・ページ範囲・ページ数・章名・合体した箇所 |
| 4 | 人 | チャットで承認または修正する（合体・分割・範囲の変更） |
| 5 | Claude | 承認された分け方の記事IDを `articles.json` の `split.approved` に書く |
| 6 | | 5のあとで、上の「新しい号を取り込む手順」の手順1以降（対象の判断、読み方の確認、重要箇所の選定、`build_issue.py`）に進む |

前書き・はじめに・目次・索引・奥付・著者紹介など、本編と関係が薄い部分は、省いてよい（人の方針）。手順3で分割案を見せるときに「対象外にする」提案として添える。`target` を `false` にするのは、人の返事を受けてから。

**承認されるまで、切り出しも重要箇所の選定も始めない**。単位が変わると、記事ID（ページ範囲）とフォルダ名（`<name>`）が変わるため。承認の記録は `split.approved` で、`target`（対象にするか）とは別の項目。どちらも人の判断で、Claude は人が承認する前に書かない。コードで止める仕組みはない（運用で守る）。
`plan_issue.py` は `split.approved` を書き換えず、一覧を作るたびに承認の状況（未承認 / 承認済み / 承認した分け方と違う）を表示する。範囲や合体を変えて承認した分け方と違ってしまったときは、再承認が要る。

```bash
cd app
# しおりの階層1を章にして分割案を作る（章が階層2なら --chapter-level 2。作り直すときは --rebuild）
uv run python plan_issue.py --pdf ../output/<書名>/<書名>.pdf --unit book
# 30ページ未満の章を、隣の章とまとめる（作り直すときは --rebuild を付ける）
uv run python plan_issue.py --pdf ../output/<書名>/<書名>.pdf --unit book --rebuild --auto-merge
# しおりがないとき: 人から聞いたページ範囲と章名で作る（FIRST-LAST:章名）
uv run python plan_issue.py --pdf ../output/<書名>/<書名>.pdf --ranges 10-35:第1章データモデル 36-60:第2章設計
# 隣接する章を合体する（一覧のIDを、並びの順に指定）
uv run python plan_issue.py --pdf ../output/<書名>/<書名>.pdf --merge p10-35 p36-60
```

- 書籍の `name` は章題から空白を除いたもの（例: `第3章データモデル`）。合体した記事は `+` でつなぐ。`articles.json` で直せる
- 分割案は、2回目以降の実行でも保たれる（範囲指定・合体は消えない）。しおりから作り直すときだけ `--rebuild`
- `articles.json` の `split` は `{"unit": "book", "approved": ["p10-35", ...]}`。`unit` は `plan_issue.py` が記録する。合体した記事には、元の章のIDが `merged` に入る
- 書名・出版社は持たない（フォルダ名で足りる）。必要になったら足す
- 元PDFが全ページ1記事のとき（記事が1つだけの書籍など）は、元PDFを作業フォルダの下のサブフォルダに `original.pdf` として移し、`articles.json` の `pdf` をその場所にする（例: `plan_issue.py --pdf <名前>/original.pdf --out articles.json`）
- 作業が終わったら原本PDFは片づけてよい。`articles.json` と `highlights/*.json` が正で、PDF は再実行で作り直せる

## ダブルクリックで始める

リポジトリ直下の **`作業開始.bat`** をダブルクリックすると、ブラウザで画面（`http://127.0.0.1:8765`、中身は `app/web.py`）が開く。ターミナルの操作は要らない。

- **PDF をアップロード**（ドロップまたは選択）すると、`inbox/` に保存して、すぐに下の取り込みを始める。`inbox/` に直接置いた PDF は「inbox のPDFを取り込む」ボタンで始める
- 画面は4ページ。左上のハンバーガーメニュー（☰）から行き来できる: **メニュー**（`/`。回答待ちの Issue があれば、ここに出る）、**新規取り込み**（`/new`。アップロードと、取り込み中のものだけ。完成した成果物は出さない）、**作業状況**（`/progress`。進行中・回答待ち）、**成果物**（`/library`。完了したもの）
- 本・号ごとに、状況（分割案を作成中 / 回答待ち / 作業中 / PDF作成待ち / 完了）が色分けで出る。質問の Issue ができたときだけ、その Issue へのボタンが出る
- 答えるのは GitHub の Issue（ボタンから開く）。仕上がりの PDF は、エクスプローラーで開く（ビューアは作らない）
- **この画面のウィンドウ（黒い画面）が開いている間、質問の Issue を2分ごとに見張る**（画面の一番下に、最終確認の時刻が出る）。回答が揃って「作業開始OK」が付くと、反映して、Claude を起動する。毎回 Issue と `articles.json` を読み直すので、分け方を変えたあとでも、古い状態のまま止まらない。ウィンドウを閉じると、見張りも止まる（もう一度ダブルクリックすれば、再開する）
- この画面は自分のPCだけで動く（`127.0.0.1` のみ。外には公開しない）。黒いウィンドウを閉じると、画面も止まる
- 以前の流れ（旧フォルダ構成・HTMLレポート）で作成済みの本・号は、作業フォルダに `完了.txt`（1行目が画面の説明になる）を置くと、状況が「完了」になる。再作成は要らない
- 画面を使わずに、手で `app/` の `uv run python start.py` を実行しても同じ（`--dry-run` で、何をするかだけ見られる）

取り込みでは、次のことを順に行う（中身は `app/start.py`）。

1. `inbox/` の PDF を `output/<PDF名>/` に移す（同名のPDFがすでにあるときは、上書きせずに止まる）
2. 移した PDF ごとに、許可を絞った Claude（`claude -p`）が、分割案を作り、本文を読み、質問の Issue（「取り込み確認: <PDF名>」）を作る。数分かかる。経過は `output/<PDF名>/claude-plan.log`
3. 回答待ち（質問の Issue が開いていて、まだ反映していない）の本・号ごとに、**見張りのウィンドウ**を開く。Issue に答えて「作業開始OK」を付けると、続き（重要箇所の選定・参考文献・Issue を閉じる）まで自動で進む

- 見張りのウィンドウを閉じたり、PC を落としたりすると止まる。もう一度ダブルクリックすれば、回答待ちの分だけ再開する
- 何をするかだけ見たいときは、`app/` で `uv run python start.py --dry-run`
- 重要箇所を選んだあとの PDF（`マーカー付き/`）は、エクスプローラーから開く（専用のビューアは作らない）
- しおりが無くて分割案が作れないとき、Claude は Issue を作らずに止まる（章名とページ範囲を人が伝える必要がある）。`claude-plan.log` に、その旨が出る

## 自動で進める

人の作業を、「PDF を置いて『作業開始』と言う」と「Issue にチェックを付ける」の2つに絞る流れ。上の各手順（分け方の承認、対象の判断、読み方の確認、仕上げ）を、次のコマンドでつなぐ。本文を読んで選ぶ部分（重要箇所、参考文献の候補）は AI が行う。

| 手順 | 誰が | やること |
|---|---|---|
| 1 | 人 | PDF を `inbox/` に置いて「作業開始」 |
| 2 | Claude | PDF を `output/<PDF名>/` に移し、分割案を作り、本文を読む（既存の手順どおり） |
| 3 | Claude | `ask_issue.py --create` で、**1つの Issue** にまとめて聞く |
| 4 | 人 | スマホなどでチェックを付ける（目的と色を選ぶ）。最後に「作業開始OK」をチェックする |
| 5 | Claude | `read_answers.py --apply --wait` が回答の揃うのを待ち、揃ったら `articles.json`（`split.approved`・`target`）と `reading.json` に写す（Issue はまだ閉じない） |
| 6 | Claude | 重要箇所と参考文献の候補を選ぶ |
| 7 | Claude | `pipeline.py --close` で、切り出し・ハイライト・リンク確認・Issue へのコメントを一括で行い、問題が無ければ Issue を閉じる |

```bash
cd app
# 3. 質問の Issue を作る（--create を外すと本文を表示するだけ。--purpose / --recommend / --emphasis は提案）
uv run python ask_issue.py --plan ../output/<書名>/articles.json --title "<書名>" --purpose 実務に使う --emphasis p125-168 --create
# 5. 回答が揃うまで待って写す（バックグラウンドで実行する）
uv run python read_answers.py --plan ../output/<書名>/articles.json --issue <番号> --apply --wait
# 7. 仕上げ（参考文献を投稿する Issue の番号を渡す）
uv run python pipeline.py --plan ../output/<書名>/articles.json --issue <番号>
```

- Issue は、**分け方と対象**（1つの一覧）と、**読み方（目的・重点・色）** を聞く。★と「推奨」は Claude の提案。決めるのは人（「人の判断」のルールは変わらない）
- **対象は、★の記事に最初からチェックを付けてある**（人の指示）。外したいものだけ外す。読み方には、チェックを付けない
- **分け方の承認のチェックは無い**。分け方を変えたくなければ何もせず、最後の「作業開始OK」で承認したことになる。変えたいときだけ「分け方を変えたい」をチェックする（`read_answers.py` が終了コード 3 で止まる）
- **最後に「作業開始OK」のチェックがある**。これが付くまで、`read_answers.py` は反映せず、作業も始めない（途中のチェック状態で動き出さないため）。分け方の承認や読み方が空のままでも、「作業開始OK」だけでは進まない
- 読み方は、目的（1つ）・使う色（1つ）を選ぶ。重点にする章は、選ばなくてもよい。「← 推奨」は Claude の提案で、答えには使わない（人が選んだものだけを使う）。目的や色が0個・複数のときは、揃っていない扱いにする
- 「分け方を変えたい」が選ばれたら、`read_answers.py` は終了コード 3 で止まる。分け方を直したあとは、Issue を作り直す（Issue の分割案が `articles.json` と違うと、揃っていない扱いになる）
- 自由に書きたいことは、Issue のコメントに書いてもらう。`reading.json` の `note` に入る
- `read_answers.py` の終了コード: 0 揃った / 2 まだ / 3 分け方の変更 / 1 エラー
- **ローカルで無人のまま進めるとき**は、`watch.py` を動かしておく: `uv run python watch.py --plan ../output/<書名>/articles.json --issue <番号>`。「作業開始OK」が付くと、反映して、ヘッドレスの Claude（`claude -p`）を起動し、重要箇所の選定から `pipeline.py` までを進める。許可は必要な操作（本文の読み書き、Python の実行、gh の Issue 操作、git のコミット・プッシュ、Web検索）に絞ってある。経過は `claude-run.log`。PC が起動していて、見張りが動いている間だけ働く（ローカル限定）。セッションを開く必要はない
- **Issue を閉じるのは、作業が終わってから**。`read_answers.py --apply` は、反映したことをコメントするだけ。`pipeline.py --close` が、マーカーの未適用も投稿の失敗も無く、参考文献が揃ったときだけ閉じる（問題があれば開いたまま）
- 参考文献を投稿する Issue は、取り込み確認の Issue とは別に作ってもよい（`pipeline.py --issue` で指定）。取り込み確認の Issue は、反映すると閉じる

## ファイル構成

```
dopagaki-publications-highlighter/
  docs/workflow.md
  app/                                   スクリプト（共通）
  inbox/                                 書籍PDFの受け取りフォルダ
  output/                                作業フォルダと成果物
    Sample-Magazine-2026年10月号/        2026年10月号の作業フォルダ（PDF名のフォルダ）
      Sample-Magazine-2026年10月号.pdf     元PDF（触らない。直下に置く）
      articles.json                      記事の一覧と、対象にするかの判断
      highlights/<ID>.json               重要箇所の元データ
      references/<ID>.json               章・記事ごとの参考文献・関連リンク（確認結果つき）
      reading.json                       読み方の答え（目的・重点・使う色）
      分割/<名前>.pdf                     記事を切り出しただけのPDF（マーカーなし。例: サンプル連載.pdf）
      マーカー付き/<名前>.pdf             ★ 読むのはこれ（重要箇所を付けた記事）
    <書名>/                              書籍の作業フォルダ（中身は号と同じ）
```

- 元PDFは作業フォルダ直下に置く（雑誌も書籍も `output/<PDF名>/`）。元PDFとして扱うのは、直下にある名前に `_` を含まないPDFだけ。`分割/` と `マーカー付き/` の中は見ない。`articles.json` の `pdf` で指定される plan 経由の実行は、この判定を通らない
- 成果物のPDFは、種類ごとの2つのフォルダに、記事の名前（`name`）で出る。切り出しただけのPDF（マーカーなし）は `分割/<name>.pdf`、重要箇所を付けたPDFは `マーカー付き/<name>.pdf`。ファイル名は章名・特集名のままなので、フォルダごと移すだけで整う。名前を変えたくなったら、出力後に手で変えてよい（再実行すると、また `name` で作り直される）
- ファイル名は `<name>.pdf`（`articles.json` の `name`）。Windows のファイル名に使えない文字（バックスラッシュ `/` `:` `*` `?` `"` `<` `>` `|`）と半角スペースは、ハイフンに置き換わる（続くときは1つ、両端は落とす。全角の `：` `？` などはそのまま）。`articles.json` の `name` は変えない。記事の `name` が重複すると衝突するので、`build_issue.py` はエラーにする。`name` を直して再実行すると、新しい名前のPDFが作られる。古い名前のPDFは生成物なので、手で消す
- `highlights/<ID>.json` と `references/<ID>.json` が正。PDF は作り直せる生成物

記事ごとにフォルダを分けるのは、重要と判断した箇所を集めて知識ネットワークにするため。連載は回をまたいで同じテーマが続くので、連載単位でも集められる。雑誌を丸ごとではなく記事単位に分けると、記事ごとに閉じた文脈で扱え、精度も上がる。他の書籍にも同じ形で広げる想定。

## 読み方を確認する

同じ本の中でも、「何のために読むか」「どこを重く見たいか」で、選ぶ箇所は変わる。そこで、**マーカーを付ける前に、人に選択式で聞く**。

- 聞くのは、**対象の本文を Claude が読んだあと**。本文を把握していれば、書籍・記事の目的や章の見出しを、Claude が先に選択肢へ入れられる。把握する前に聞くと、選択肢が一般論になる
- 書籍は、分け方の承認（`split.approved`）と対象の判断が済んでから。雑誌は号ごと、書籍は1冊ごとに1回
- 答えは人の判断。Claude は人に代わって答えない。選択肢に合うものがなければ、「その他」で自由に書いてもらう

前提は、**マーカーを付けた箇所が、そのまま書籍（記事）の要約になる**こと。マーカーだけを読んで内容がつかめるように選ぶ（[人が示した基準](highlight-criteria.md)の「`text` 単体で伝わる」「推測で埋めずに済む」を満たす）。「周辺の要約」と「全体を通したハイライト」の2段階は設けない。段階を分けると、基準がぶれるため。読むためにその本を選んでいるので、「知る」を重視するかも聞かない。

聞くことは次の3つ。聞き方は2通りで、どちらも1回で聞ける。選択肢の文言は、本文に合わせて変えてよい。

- **チャットの選択式**（AskUserQuestion）: その場で答えるとき
- **GitHub Issue のチェックボックス**: スマホなど、ターミナル以外で答えたいとき。下の「Issue で聞く」

| 聞くこと | 選択肢の例 | 選び方への効き方 |
|---|---|---|
| 目的（何のために読むか） | 概要をつかむ / 実務に使う / 体系的に学ぶ / 後で探すための索引にする | 色とラベルの配分が変わる（下の「目的ごとの配色」）。重点の章とは別に効く |
| 重点にする章・見出し（複数可） | Claude が見出しから挙げた候補（章名・節名）/ 特になし | 重点にした箇所は、ほかより気持ち多めにマーカーを付ける。数は統一しない。章ごとに密度が違うのは、そのままでよい |
| 使う色（2色か3色） | 3色（注意は主張に直結するものだけ）/ 3色（注意を積極的に）/ 2色（知る・方針・実践。注意は使わない）/ 2色（方針・実践・注意。知るは使わない） | 使わない色は、一切付けない。目的からの既定は「目的ごとの配色」。答えがあれば、答えを優先する |

- 「気持ち多め」は、数で決めない。目安（1ページ3〜4か所）に対して、重点にした章・見出しでは、1ページに1か所ほど多くなってもよい、程度に読む（暫定）
- 色は、必ずしも3色である必要はない。**2色か3色**で、使わない色は付けない。ラベル（`definition` など）は、使う色の中から選ぶ
- 注意（赤）を使うときの扱い（積極的に / 主張に直結するものだけ）は、色の答えに含める。実績が溜まってから基準にする。いまは、聞いた答えどおりに選ぶだけ
- 色とラベルの定義は `app/apply_highlights.py` の `GROUPS` / `CATEGORIES`。ここには複製しない

### 目的ごとの配色

目的が違えば、使う色もラベルも変わる。次は、Issue やチャットで推奨として示す既定。色の答えがあれば、答えが優先。

| 目的 | 色 | 厚めにするラベル | 件数の考え方 |
|---|---|---|---|
| 概要をつかむ | 2色: 知る・方針・実践 | `principle`（章・記事の主張）。`definition` は、鍵になる用語だけ | 少なめ。章ごとに主張が追える程度 |
| 実務に使う | 3色 | `practice`・`warning`。`definition` は、実務で使う用語だけ | 標準 |
| 体系的に学ぶ | 3色（注意は主張に直結するものだけ） | `definition`・`principle` | 標準から多め |
| 後で探すための索引にする | 2色: 知る・方針・実践 | `definition`。`principle` は見出しの代わり | 用語・概念の数に応じる。注意（赤）は使わない |

- 重点にした章・見出しは、この配色のうえで、さらに気持ち多めにする
- 色を変えたときも、「人が示した基準（確定）」（`text` 単体で伝わる、推測で埋めずに済む）は変わらない
- 実績は、[records.md](records.md) の表に残す。目的ごとの配色は、まだ実績が無いので暫定

### Issue で聞く

1. Claude が、本文を読んだあとに Issue を1つ立てる。タイトルは `読み方の確認: <書名または号>`。リポジトリは非公開だが、公開に変えるときは先に人に確認する
2. 本文は上の3問。選択肢を `- [ ]` で並べる。重点にする章は複数可、目的は1つ、使う色は組み合わせを1つだけ選ぶと書く。目的ごとの既定は、選択肢の横に推奨として書く（チェックは付けない）。「その他」は、コメントに自由に書いてもらう
3. 人が、スマホの GitHub アプリなどでチェックを付ける（コメントでもよい）
4. 人が「答えたよ」と伝えたら、Claude が `gh issue view <番号> --comments` で読み、`reading.json` に写す。チェックが0個や、1つのはずが複数のときは、人に聞き直す。Claude は人に代わって答えない
5. 写し終えたら、Issue に「`reading.json` に反映した」と書いて閉じる

答えの記録は `reading.json` が正で、Issue は入力の窓口。

答えは、作業フォルダ（`output/<PDF名>/`）の `reading.json` に残す。スクリプトは読まないが、あとから「なぜこの選び方をしたか」を説明する材料になる。

```json
{
  "answered": "2026-11-14",
  "purpose": "実務に使う",
  "emphasis": ["第3章 データモデル", "第5章 リトライ設計"],
  "colors": ["know", "do", "warn"],
  "warning": "記事の主張に直結するものだけ",
  "note": "自由記述（例: 第8章は読み飛ばす）"
}
```

- 項目はすべて省略できる。`emphasis` は、章名・節名など見出しのテキスト。`colors` は使う色（`know` 知る / `do` 方針・実践 / `warn` 注意）で、2つか3つ。省略したときは3色とみなす。`warning` は、`warn` を使うときだけ書く
- 答えが変わったら `reading.json` を直す。影響する記事の重要箇所を選び直すかは、人に聞く
- `reading.json` は、重要箇所を選ぶときの前提であって、「人が示した基準（確定）」の代わりにはならない。両方を満たす

## 重要箇所の選び方

選定は、本文と参考リンクを読み、上の「読み方を確認する」の答えを踏まえて判断する工程。結果を `highlights/<ID>.json` に残すと、PDF のハイライトが機械的に作られる（同じJSONなら同じ結果）。

| 色 | 意味 | 含まれるラベルと選ぶ基準 |
|---|---|---|
| 青 | 知る | `definition` 定義: 用語の意味<br>`evidence` 根拠・数値: 研究・計測の数値。主張を裏づける事実 |
| 緑 | 方針・実践 | `principle` 原則・主張: 結論・設計方針。記事の主張を理解するのに欠かせない文<br>`practice` 実践: 具体的にやること。導入・運用の手順や方針 |
| 赤 | 注意 | `warning` 注意・限界: やってはいけないこと、成り立たない条件、手法の限界 |

色は4色ボールペンの発想で3色（黒＝通常の文字）。PDFには色だけを付ける（コメントは付けない）。下位のラベルは JSON に残る。
色とラベルの定義は `app/apply_highlights.py` の `GROUPS`（色）と `CATEGORIES`（ラベル）が唯一の定義。

### 目安

- 1ページあたり3〜4か所。記事の主張を追うのに欠かせない箇所に絞る
- 参考リンクがある数値・主張は、公式ページや論文の要旨で確認し、裏づけが取れた箇所にだけ「照合」の印を付ける（印のない箇所は本誌の記述に基づく選定）
- `text` は改行位置・空白・全角半角が違っても一致する。脚注番号・ふりがな・段をまたぐ文は途切れるので、短く区切る
- 一致するかは `uv run python apply_highlights.py --pdf <切り出したPDF（分割/<name>.pdf）> --highlights <JSON> --dry-run` で確認できる

### 選定基準

何を選ぶかの基準は [highlight-criteria.md](highlight-criteria.md) にまとめてある。既存の結果から判断できることだけを書いた**暫定版**で、選んだ長さ・`reason` の書き方・ラベルの使い分け・件数・照合の実績と、「分かっていないこと」が入っている。選ぶ前に読む。新しい号を処理したら、その文書の実績の表に行を足す。基準を確定させる作業は [#7](https://github.com/eno-conan/magazine-highlighter/issues/7)。

### JSON の形式

```json
{
  "meta": {
    "title": "題",
    "source_pdf": "対象PDFの説明",
    "page_offset": 99,
    "references": [
      {"id": "aws-sqs-dlq", "name": "表示名", "url": "https://...", "checked": "何を確認したか", "result": "verified"}
    ]
  },
  "highlights": [
    {"page": 6, "text": "ハイライトする本文", "category": "definition", "reason": "なぜ重要か",
     "verification": "verified", "refs": ["aws-sqs-dlq"], "check": "照合結果のメモ", "occurrence": 1}
  ]
}
```

- `page`: 切り出したPDFのページ番号（1始まり）。`page_offset` は、元PDFのページ（`page + page_offset`）を知りたいときの差
- `verification` / `result`: `verified` 照合済み ／ `partial` 一部照合 のどちらか。省略可
- `refs`: `meta.references` の `id`。存在しない `id` は読み込み時にエラーになる
- `meta` と `reason` / `check` / `refs` / `occurrence`（同じ文が複数あるときの何番目か）は省略できる

> JSON には本誌の本文の抜粋が入っている。リポジトリを公開する場合は、載せてよいか確認すること。

## 参考文献を集める

章・記事ごとに、読んだあとに深掘りできる参考文献・関連リンク（公式ドキュメント、論文、解説記事など）を集めて、読み方の Issue にコメントする。マーカーの箇所に限らない。HTMLのレポートは作らない。

| 手順 | やること |
|---|---|
| 1 | 本文に出てくるURL・文献を拾い、足りなければ WebSearch で公式ドキュメントなどを探す。`references/<ID>.json` に書く |
| 2 | `check_links.py` で全リンクを実際に取得して `status` を付ける |
| 3 | `blocked`（403・429・503）のものは、Claude in Chrome で実ブラウザから開いて確認する。開けて、ログインも要らなければ、`status` を `ok`、`verified_by` を `browser` にする |
| 4 | `post_references.py` で、`ok` のものだけを、1章1コメントで読み方の Issue に投稿する |

載せない基準（3つの懸念への対処）:

- **404になるもの**: 取得して200でないものは載せない（`not_found`）
- **ボット扱いで取れないもの**: ふつうのブラウザ相当の User-Agent で取りに行く。それでも断られたら、実ブラウザで開けたものだけ載せる。ボット対策（CAPTCHAなど）の回避はしない
- **ログインが必要なもの**: 401、ログイン画面へのリダイレクト、会員限定の文言、パスワード欄だけのページは載せない（`login`）。判定が怪しいものも載せない

並べ方（技術書に限らず、どの分野の本・記事にも使う）: **JSON の配列の順がそのままコメントの順**。「見ると有益な順」に並べる。目安は次のとおり。

- 先頭に置く: 読み終えてすぐ役に立つもの、手を動かして確かめられるもの（登録なしで触れるデモ、短い手引き）、一次資料で全体像をつかめるもの
- 中ほど: 個別の話題を深掘りするもの、本文で紹介された道具・文献の公式資料
- 後ろ: 参照用の辞書、国内外の方針など、必要になったときに引くもの
- `summary` には、「何のページか」ではなく**「なぜ見る価値があるか」**（本文のどこが深まるか）を1文で書く

`references/<ID>.json` の形式:

```json
{
  "title": "第1章 ログの基礎知識",
  "references": [
    {"url": "https://docs.python.org/3/library/logging.html", "title": "logging — Python 公式",
     "kind": "official", "summary": "標準ライブラリのログの仕様"}
  ]
}
```

- `kind`: `official` 公式 / `paper` 論文 / `article` 記事 / `book` 書籍 / `tool` ツール / `video` 動画 / `course` 講座 / `site` サイト。省略可
- `status` `http` `final_url` `note_check` `checked` は `check_links.py` が書く。手で書くのは `verified_by: "browser"` だけ
- 同じ章のコメントがすでにあるときは、重複して投稿しない（コメント先頭の目印 `<!-- references:<ID> -->` で判定）。直したときは、JSON を直して `post_references.py --update --issue <番号>` で、すでにあるコメントを書き換える
- 読み方の Issue を閉じていても、コメントは投稿できる。必要なら開き直してよい

## セットアップ

[uv](https://docs.astral.sh/uv/) が必要（Issue のコメントを使うときだけ [GitHub CLI](https://cli.github.com/) も）。

```bash
cd app
uv sync
```

## 個別に使う

| 目的 | コマンド |
|---|---|
| 記事を1つだけ切り出す | `uv run python split_pdf.py --pdf ../output/Sample-Magazine-2026年10月号/<号>.pdf --first 120 --last 126 --name サンプル連載`（出力は元PDFと同じフォルダに `<元名>_<name>.pdf`。`--out` で場所を指定できる） |
| 重要箇所が PDF に一致するか確認 | `uv run python apply_highlights.py --pdf <切り出したPDF> --highlights <JSON> --dry-run` |
| ハイライトだけ付ける | `uv run python apply_highlights.py --pdf <切り出したPDF> --highlights <JSON>`（出力: `<PDF名>の重要箇所.pdf`） |
| 参考リンクを確認する | `uv run python check_links.py --refs ../output/<書名>/references/<ID>.json`（結果は JSON の `status` に書き戻る） |
| 参考文献を Issue に投稿する | `uv run python post_references.py --refs <JSON> --issue <番号> --post`（`--post` を外すと本文を表示するだけ） |

### Issue のコメントをマーカーにする（当面使わない）

試験的に作ったもので、コードだけ残してある（`app/mark_pdf.py`）。Issue のコメントの先頭行にページ番号（`P20`）、blockquote に引用を書くと、その箇所にハイライトを付ける。

```bash
uv run python mark_pdf.py --pdf ../output/Sample-Magazine-2026年10月号/Sample-Magazine-2026年10月号.pdf --offset 14 --dry-run
```

## 制約

- 画像PDF（スキャン）は文字を検索できない。文字が取れない記事は自動で対象外になる
- ふりがな・脚注番号・図版の文字が混ざる箇所は、重要箇所の `text` が途切れる（短く区切る）
- パスワード付きPDF（空パスワード以外）は未対応
- 出力PDFの置き換えが遅い環境がある（Windows。既存の大きなファイルの削除に数十秒かかることがある）
