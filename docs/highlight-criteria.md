# 重要箇所の選定基準（実績から整理した暫定版）

重要箇所（`highlights/<ID>.json`）を選ぶときに参照する、号をまたいで使う文書。

## この文書の位置づけ

- 既存の結果から、**判断できることだけ**を書いた。先に決めた基準ではなく、選んだ結果の整理なので**暫定**
- 例外は「人が示した基準（確定）」の節。実績ではなく、使う人が示した基準で、暫定ではない
- 根拠にした結果は、[records.md](records.md) の表にある。号や書籍を処理したら、表に行を足す
- 実績から判断できないこと（選ばなかった箇所の基準など）は「分かっていないこと」にまとめる。ここに書いていないことを、推測で補わない
- 色とラベルの**定義**は `app/apply_highlights.py` の `GROUPS` / `CATEGORIES` が唯一の定義。この文書には複製せず、ラベル名と実績の傾向だけを書く
- 作業の流れ、JSON の形式は [workflow.md](workflow.md) を参照

## 選ぶ単位と書き方

実績から言えること。

- `text` は短い文、または文の一部。長さは12〜126字、中央値は約47字。段落を丸ごと選んだ例はない
- 複数の文にまたがる `text` は406件中25件（約6%）。基本は1文
- 全件に `reason` がある。中央値は約18字で、1行
- `reason` に書いている内容は、「何の定義か」「何の仕組みか」「何の長所と短所か」「なぜ注意が要るか」「どの課題を挙げているか」など、**その箇所が記事の中で担う役割**
- 本文が後で内容を見直す場合は、`reason` にその旨を書いている（例: 「ただし単純な整理で、後で見直される」）
- 著者が例として挙げた数値は `evidence` にして、`reason` に「著者の例示」と書いている
- `occurrence`（同じ文が複数あるときの何番目か）を使った例は0件

## ラベルごとの実績

ラベルの定義は `app/apply_highlights.py` の `CATEGORIES`。ここでは、ある雑誌1号の9記事で、そのラベルに入れたものの傾向だけを書く。

| ラベル | 入れたもの（`reason` から） |
|---|---|
| `definition` | 用語の意味、問題が起きる仕組み（例: 結果の行数が膨らむ仕組み） |
| `evidence` | 数値、計測結果、著者の例示のデータ量・件数 |
| `principle` | 記事が向き合う課題の整理、設計方針、主張、手法の長所と短所 |
| `practice` | 使い分けの指針、設定のタイミング、確認すべきこと |
| `warning` | 見積もれない、解決できていない、メモリを圧迫する、切り替えが堂々巡りになる、といった限界や落とし穴 |

- 手法の「長所と短所」の整理は、`principle` に入れた例がある（`warning` ではない）
- 記事によって、ラベルの構成比は大きく違う（[records.md](records.md)）。記事の性質によるものか、選び方の揺れかは、実績からは分からない

## 件数

- 1ページあたり3〜4か所が目安（[workflow.md](workflow.md)）
- 実績は、**ハイライトのあるページあたり**で、おおむね 2〜5 か所。記事の中では、1ページに1〜7か所
- ハイライトの無いページがある。**全ページに付けているわけではない**
- 記事ごとの差が、記事の密度によるものか、判断の揺れかは分からない

## 照合（`verified` / `partial`）

実績から言えること。

- 雑誌1号の実績では、406か所のうち46か所（`verified` 38、`partial` 8）に印を付けた。残り360か所は、本誌の記述に基づく選定（印なし）
- 照合に使ったのは、参考リンクとして `meta.references` に登録した出典。全件に `check`（何を確認したか）がある
- 確認先は、公式ドキュメント、公式ブログ、料金などの公式ページ、仕様、技術記事、論文。論文は**要旨を確認**している（`check` に「要旨」と書いてある）
- **照合は `evidence` に偏る**。ラベル別の照合率は次のとおり

  | ラベル | 照合した件数 / 全件数 |
  |---|---|
  | `evidence` | 18 / 38（47%） |
  | `definition` | 10 / 78（13%） |
  | `warning` | 8 / 92（9%） |
  | `practice` | 4 / 72（6%） |
  | `principle` | 6 / 126（5%） |

- `partial` にした8件の共通点は、**趣旨は出典と一致するが、その一部が確認できなかった**こと。未確認だったのは、数値（論文の要旨に数値がない）、用語そのもの、改称の経緯、特定条件での数値
- `verified` は、`check` に出典で確認した内容を書いてある

## 人が示した基準（確定）

実績からの整理ではなく、使う人（ユーザー）が示した基準。2026-10-14 時点で確実に言えるとされたもの。選ぶとき・見直すときは、これを満たすかを確かめる。

1. **`text` 単体で内容が伝わること**。前後の文を読まなくても、何の話か分かる。特に数値は、主語が欠けると何の話か分からない
   - 悪い例: 「最初の合格率は22％です」（何の合格率か分からない）、「削減率はほぼ見積もりどおり、実測でも約50％になりました」（何の削減率か分からない）
2. **集めた `text` から記事のサマリーを作るとき、単語間を推測で埋めずに済むこと**。`text` を並べただけで、つながりが読み取れる。推測が要る文は選ばない（または範囲を広げて、必要な語を含める）

- `text` は PDF の本文と一致させる必要があるので、書き換えて主語を補うことはできない。補うなら、主語を含む箇所まで範囲を広げる（実績の中央値約47字より長くなりうる）
- `reason` で補う方法は、1. の「`text` 単体で」を満たさないので、この基準の解決にはならない
- 既存の選定が、この2つを満たすかは未確認（下の「分かっていないこと」）

## 読み方による調整（人が選ぶ）

実績ではなく運用。マーカーを付ける前に、目的・重点にする章や見出し・使う色（2色か3色）を、人が選択式で選ぶ。答えは作業フォルダの `reading.json`。聞き方と、答えの選び方への効き方は [workflow.md](workflow.md) の「読み方を確認する」。

- **マーカーの集まりが、そのまま書籍（記事）の要約になる**。「周辺を読んで判断できる箇所」と「書籍全体を通して言える箇所」の2段階には分けない（段階を分けると基準がぶれるので採らない）
- 量は統一しない。重点にした章・見出しを気持ち多めにする。「気持ち」の具体的な幅は暫定
- 以降に選んだ号・書籍は、`reading.json` の答えが「なぜこの選び方か」の説明になる。読み方を聞く前に選んだものは、`reading.json` が無い

## 分かっていないこと

実績からは判断できない。

- **「人が示した基準」を、既存の選定が満たす割合**。満たさないものを、範囲を広げて直すか、現状を許容するか
- 範囲を広げて主語を含めると `text` が長くなる。「短い文、または文の一部」という実績の傾向と、どう折り合うか

- **色の使い方（2色か3色か、注意の扱い）と配色を、目的によってどう変えるか**。`reading.json` の `colors`・`warning` の答えと、実際に選んだ注意の件数・内容を溜めて、基準を作る
- **選ばなかった箇所の基準**。何を選ばなかったかの記録がない
- 件数・ラベル構成のぶれの理由（記事の性質か、揺れか）
- 照合の対象にする箇所の基準。参考リンクの登録も照合も0件の記事があり、調べなかったのか、対象が無かったのかは記録がない
- 同じ内容が複数箇所に出たときの扱い
- 特集と連載で、選び方を変えたか
